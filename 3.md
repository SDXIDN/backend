# Лабораторна робота №3

**Тема:** Анотації  
**Дисципліна:** Розробка високонавантажених корпоративних систем  
**Виконав:** ПІБ, група

## Мета
Реалізувати три кастомні анотації різних типів, кожна з яких демонструє окремий механізм Spring Boot: Bean Validation constraint, композитна (meta) анотація та анотація-резолвер аргументів MVC.

| № | Тип | Анотація | Файли |
| :--- | :--- | :--- | :--- |
| **1** | Bean Validation constraint | `@ValidBookingTimeRange` | `validation/*` |
| **2** | Композитна анотація | `@CreatedPost` | `annotation/CreatedPost.java` |
| **3** | Резолвер аргументів MVC | `@CurrentUsername` | `web/*`, `config/WebConfig.java` |

Кожен механізм використано рівно один раз, повторів немає.

## Тип 1. Bean Validation: `@ValidBookingTimeRange`
Класова анотація до DTO `CreateBookingRequest` перевіряє часовий проміжок бронювання як нове бізнес-правило (а не копію `@ValidSkuCategory`): кінець після початку, тривалість від `minMinutes` (15) до `maxMinutes` (480) та початок і кінець в межах однієї доби.

```java
@Documented
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = BookingTimeRangeValidator.class)
public @interface ValidBookingTimeRange {
    String message() default "Invalid booking time range";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
    long minMinutes() default 15;
    long maxMinutes() default 480;
}
```

Валідатор `BookingTimeRangeValidator implements ConstraintValidator<ValidBookingTimeRange, TimeRangeSource>` працює через інтерфейс `TimeRangeSource` (`getStartTime()`, `getEndTime()`), тому не прив'язаний до конкретного DTO. Для кожного порушення будується окреме змістовне повідомлення (`buildConstraintViolationWithTemplate` + `addPropertyNode("endTime")`):
* `endTime must be after startTime`;
* `booking is too short: 5 min, minimum is 15 min`;
* `booking is too long: 481 min, maximum is 480 min`;
* `booking must start and end on the same day`.

Анотація застосована до `CreateBookingRequest` разом із `@Valid` у контролері; помилка перетворюється на `400` із повідомленням `endTime: endTime must be after startTime`.

## Тип 2. Композитна анотація: `@CreatedPost`
Об'єднує `@RequestMapping(method = POST)` та `@ResponseStatus(HttpStatus.CREATED)` — аналог того, як `@RestController` об'єднує `@Controller` і `@ResponseBody`. Атрибути `value` і `path` прокинуті через `@AliasFor`:

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@RequestMapping(method = RequestMethod.POST)
@ResponseStatus(HttpStatus.CREATED)
public @interface CreatedPost {
    @AliasFor(annotation = RequestMapping.class, attribute = "value")
    String[] value() default {};

    @AliasFor(annotation = RequestMapping.class, attribute = "path")
    String[] path() default {};
}
```

Використання у `BookingController`:

```java
@CreatedPost
@PreAuthorize("hasRole('USER')")
public BookingDto create(@Valid @RequestBody CreateBookingRequest request) { ... }
```

| **5** | Порівняння з оригінальними анотаціями через MockMvc (той самий статус 201, routing, 405 для неправильного методу) | `request_composedAndOriginal_behaveIdentically`, `request_wrongHttpMethod_bothReturn405`, `bookingController_create_returns201WithBody` |

## Тип 3. Резолвер аргументів: `@CurrentUsername`
Анотація `@CurrentUsername` (`@Target(PARAMETER)`) дозволяє контролеру отримати ім'я поточного користувача без повторення логіки видобування. `CurrentUsernameArgumentResolver implements HandlerMethodArgumentResolver` читає `Authentication` із `SecurityContextHolder` і повертає `CurrentUser.username()`. Резолвер реєструється у `WebConfig.addArgumentResolvers`.

```java
@Override
public boolean supportsParameter(MethodParameter parameter) {
    return parameter.hasParameterAnnotation(CurrentUsername.class)
            && String.class.equals(parameter.getParameterType());
}
```

Використання в `ApiController`:

```java
@GetMapping("/api/secure/username")
public String username(@CurrentUsername String username) {
    return "Hello, " + username;
}
```

| AC | Підтвердження | Тест (`CurrentUsernameArgumentResolverTest`) |
| :--- | :--- | :--- |
| **6** | `supportsParameter` $\rightarrow$ `true` для анотованого параметра, `false` для неанотованого | `supportsParameter_annotatedStringParameter_returnsTrue`, `supportsParameter_parameterWithoutAnnotation_returnsFalse` |
| **7** | `resolveArgument` повертає правильне значення потрібного типу (`String`) | `resolveArgument_authenticatedUser_returnsUsernameAsString`, `resolveArgument_noAuthentication_returnsNull` |
| **8** | Реальний запит через MockMvc: значення використовується в тілі відповіді | `request_secureUsername_resolvedValueIsUsedInResponseBody` $\rightarrow$ `Hello, bob` |

## Висновок
Реалізовано три анотації трьох різних типів: constraint-валідацію з власним бізнес-правилом, композитну анотацію на основі meta-annotations та `@AliasFor`, а також анотацію з `HandlerMethodArgumentResolver`. Усі вони використовуються в робочому коді та покриті unit-тестами без запуску Spring-контексту.
